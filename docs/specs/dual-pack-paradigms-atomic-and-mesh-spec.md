# 整合包部署预设：Atomic 与 Mesh

本规格约束可选 Launcher／Runtime 的部署行为。两种模式是可调整的部署预设，不限制程序形态，不是 Hub 业务模型，也不表示多进程业务事务具有原子性。Hub 继续只处理身份、枢纽桥权限、信息路由与留存。

## 1. 已有基础与本轮范围

现有实现已经支持运行中添加、独立启停及移除受管模块，审阅外部程序接入，以及实际组合的源码快照与版本保存。全局 Hub 已有授权接入、静态装配和组合版本更新。本轮复用这些能力，补充启动预设、按需启动、关键成员保护及对应界面，不能重建一套绕过审阅的控制路径。

用户已选择：**采用可调整预设，保留现有动态能力**。Atomic 和 Mesh 均可进入动态装配、控制单成员并授权外部程序；名称不代表封闭与开放的安全等级。

## 2. 模式与策略

| 项目 | Atomic：整组启动预设 | Mesh：协同空间预设 |
| --- | --- | --- |
| 初次启动 | 按 `autostart` 选择成员；选中集合须全部完成启动条件，失败则清理本次所属进程 | 同样按 `autostart` 选择成员；默认 independent 下非关键运行失败只记录该成员并继续无关项 |
| 缺省运行故障策略 | `fail-fast` | `independent` |
| 高级覆盖 | 可明确选择 `independent` | 可明确选择 `fail-fast` |
| 单成员动态控制 | 同一审阅链与状态表快捷入口 | 同一审阅链与状态表快捷入口 |
| 外部程序接入 | 必须授权，不接管进程 | 必须授权，不接管进程 |
| 整包停止 | 等待全部所属进程退出后停止 Hub | 同样等待全部所属进程退出，不终止外部自管进程 |

`autostart` 决定初始计划成员，`after` 决定启动前置，`packType` 决定初始集合的失败约束，`lifecyclePolicy` 决定意外故障处理；在 Mesh 中也决定实际非关键初始启动失败后是否继续。Atomic 初始全成约束仅针对本次选中集合；Mesh 显式改成 fail-fast 后，实际启动失败也会停组。界面选择预设会同时设置其缺省故障策略；随后允许单独修改策略，并分别显示两者。不得用 `packType === "mesh" || lifecyclePolicy === "independent"` 猜测类型。

Atomic 不承诺业务操作回滚或端到端成果成功。Mesh 不承诺应用自动发现、自动重试、自动替换提供者或业务容错；这些能力由程序实现。

## 3. 当前声明扩展

继续使用当前 `world-hub.pack/v1` 与 `world-hub.pack-lock/v2`，完整源码及声明进入审阅摘要。以下字段是当前规范的可选字段，不引入旧格式运行器、迁移器或协议降级。

| 字段 | 类型与缺省值 | 精确定义 |
| --- | --- | --- |
| `packType` | `atomic` 或 `mesh`，省略为 `atomic` | 不从其他字段推断类型 |
| `lifecyclePolicy` | `fail-fast` 或 `independent` | 显式值优先；省略时 Atomic 为 fail-fast，Mesh 为 independent |
| `components[].autostart` | boolean，省略为 true | 两种预设初始计划是否尝试启动该成员；false 的成员可后续单独审阅启动 |
| `components[].critical` | boolean，省略为 false | 该成员被请求启动后，关键启动失败或意外运行失败需要停止整包；主动停止不属于意外失败 |

未知字段及错误类型明确拒绝。缺省值是当前契约规定，不能借缺省值改写导入的源码或锁。摘要可以显示有效值，原始声明仍保留作者的显式值与省略状态。

```json
{
  "packType": "mesh",
  "lifecyclePolicy": "independent",
  "components": [
    { "id": "engine", "module": "demo.engine", "autostart": true, "critical": true,
      "after": [], "settings": {}, "bridges": { "main": { "publish": ["core"], "subscribe": ["core"] } } },
    { "id": "translator", "module": "demo.translator", "autostart": false, "critical": false,
      "after": ["engine"], "settings": {}, "bridges": { "main": { "publish": ["trans"], "subscribe": ["trans"] } } }
  ]
}
```

上例是字段片段，不是完整可执行包。完整声明仍需主题表、精确能力绑定、入口、期限和源锁。

## 4. 启动、依赖与故障

### 初始启动

1. 先核对全部锁定源码、权限、平台与解释器环境，取得审阅授权和实例排他所有权。
2. 建立每个受管成员的真实状态行，再启动专属 Hub。尚未尝试的成员使用 stopped、neverStarted 与空 PID，不编造退出回执。
3. 两种预设均跳过 `autostart:false`；手动成员不会因其他程序依赖它而被偷偷启动。
4. Atomic 按声明拓扑尝试初始计划成员；任一选中成员启动失败或前置受阻，均清理本次所属进程。
5. Mesh 中，前置成员未就绪时记录 `blockedBy`，不执行该成员，无关项继续。被请求自动启动的关键成员遭阻塞也视为关键启动失败。
6. Mesh 采用 independent 时，非关键成员的实际启动失败须确认该成员所属进程已退出，再继续启动无关项；显式 fail-fast 则停止整组。两型全部成员手动时都允许 Hub 运行、成员数为零、入口 URL 为空。

本次还可明确选择仅启动 Hub，执行审阅绑定 `startupMode:"hub-only"`，默认使用 `"plan"`。该选择不重写包声明与锁，也不改变之后独立启动的条件。

源码或解释器漂移、用户取消、Hub 故障、非法声明、清理未确认及其他部署安全错误不能被“非关键”吞掉。当前参考实现仍预检全部锁定解释器，不宣称手动 Python 成员缺少解释器时也能通过整包环境检查。

### 启动依赖与能力绑定

`after` 始终表示明确的启动前置条件，必须无环。界面箭头不能改称信息消费方向或纯推荐顺序。

`bindings` 表示确切的能力提供者与消费者声明，不证明其在线或业务成功。两种预设均不将能力绑定额外解释为隐式启动依赖；需要严格启动先后时由作者填写 `after`。提供者暂时离线后的等待、重试及恢复由程序处理。

显式启动手动成员也须检查当前 `after` 条件。启动审阅不会自动启动其前置成员。单成员停止不会自动终止依赖它的其他程序；业务可用性须另行观察。

只读预检发现前置未就绪时应拒绝生成该启动审阅，不停止任何程序。这不同于已授权的整包初始启动中关键成员遭到阻塞，也不同于接受审阅后实际启动关键成员失败。

### 意外故障与关键成员

- 启动完成后，`independent` 保留其他成员与 Hub，记录失败成员及诊断；`fail-fast` 停止整组。
- `critical:true` 的被请求启动失败、启动阻塞、意外退出（包括退出码 0）、健康失败或通信失联触发整组停止，即使显式选择 independent。
- `critical:true, autostart:false` 的成员尚未被请求启动时，不构成启动失败。
- 经审阅的主动停止不等于关键故障。移除仍须先处理入口、能力绑定和启动依赖。
- 停止以实际所属进程句柄及退出证据为准；不能从状态文件 PID 推断所有权或直接杀进程。

上述 autostart、critical 保护适用于 Runtime 拥有的受管进程。外部授权接入只建立通信身份，程序自行管理其启动、健康和退出；不能对外部成员宣称相同的关键进程保护，界面也不提供这两个受管标志的设置。

## 5. 控制接口与运行观察

复用现有 Runtime 私有控制接口：`GET /assembly`、`POST /assembly/preview`、`POST /assembly/apply`。Launcher 复用 `/api/instances/:id/assembly/...`。

状态表的行内启动／停止也走读取当前组合 → 获取精确修订审阅 → 用户明确接受 → 应用 → 观察异步结果。继续绑定实例、runId、revision、源码与解释器摘要、有限期 review 和所属进程队列。不新增无审阅的 `/components/:id/start` 直通 spawn 接口。

当前动态修改只支持 trusted-local。Mesh、部分启动或仅 Hub 模式对不支持的隔离 profile 明确拒绝，不静默退回本机运行。Atomic 的全成员初始启动保持既有隔离范围。

实例摘要必须从真实包及当前运行状态给出 `packType`、有效故障策略和逐组件标志，覆盖导入、恢复、升级、保存及重新关联。启动预设、声明状态、进程、通信、就绪、健康与业务完成各自区分。运行配置继续是启动快照，不因切换界面或修改草稿自动注入正在运行的程序。

## 6. 工作台与实例界面

- 工作台提供双语 Atomic／Mesh 选择器和独立故障策略设置；选择预设时说明将采用的缺省值。
- 组件编辑和新增表单提供加入初始计划、critical 与显式前置。切换预设保留已填写的标志；能力提供者选择不自动更改启动前置。
- 草稿保存、刷新恢复、替换预检、另存新组合、原实例新版本保存和锁定均完整保留字段。两种保存出口仍要求更高组合版本；模块作者版本不变。
- 详情分别展示启动预设和运行故障策略，不能标成业务“确定性交付”。
- 两型状态行提供审阅启动／停止及日志，显示手动、关键和阻塞原因。外部自管程序不出现受管启停按钮。
- 操作必须针对确切实例、运行和成员，展示执行中状态；不把接受请求显示为已启动或已退出。陈旧观察、未确认清理和不支持的隔离状态不得误开放操作。
- Atomic 保留既有动态装配高级入口；不因名称限制程序或撤销用户已有控制能力。

## 7. 全局 Hub 与版本互通

全局 Hub 是可授权的本机共享通信环境，不是无认证的公共 WS 总线。它已经具有独立程序管理、静态装配、源码导出和参数／接线版本更新。

从全局 Hub 载入工作台后，可选 Atomic 或 Mesh 导出独立包，重新导入并审阅启动。全局 Hub 的启动计划与 autostart、after 互通；直接更新还可应用这些计划字段。该目标仍不执行 packType、整包故障策略或 critical；不支持的声明必须明确拒绝并提示另存为包。详见[启动计划](startup-plans-spec.md)。

整合包升级审阅应展示模式、故障策略及组件启动／关键标志变化。保存和升级不推测业务数据格式，不自动运行迁移；继续使用提供者声明与明确的数据策略。外部接入凭据和自管程序源码不进入公开包。

## 8. 验收范围

- Atomic 初始选中成员任一失败清理全组，未选成员保持停止；两种模式均保留经审阅的动态控制。
- 两型全手动及仅 Hub 模式：Hub 在线、成员未被暗启、入口为空且状态真实。
- Mesh 可选成员启动失败，无关成员与 Hub 持续运行；被阻塞成员有明确原因。
- 关键成员启动阻塞／失败和运行故障触发整组停止；主动停关键成员不误判为故障。
- 高级故障策略覆盖与预设分开显示和执行，不依据 policy 猜 type。
- 确切能力绑定与 after 各自验证，不把离线服务等同于不存在的契约。
- 两语工作台选型、组件标志、草稿恢复、新版本导出和原实例保存闭环。
- 行内操作仍须审阅并接受，过期、跨实例、跨运行及外部所有权不能绕过。
- 原动态装配、全局 Hub 参数接线、升级与分发安装回归。
- 故障注入仅由测试保留的确切 ChildProcess／所属树句柄发起，清理后核对实际退出。

实现证据以实际进程、真实枢纽桥通信及保存后重启为准。静态图、Schema 或按钮存在本身不构成业务验收。相关基础见[动态装配规格](dynamic-pack-assembly-spec.md)、[本机 Hub 静态装配](global-hub-static-assembly-spec.md)与[部署规范](../ecosystem/pack-spec.md)。

# 启动计划：成员、顺序与后续启用

启动计划属于可选 Launcher／Runtime 的进程管理。Hub 只接纳和转交通信，不解释程序业务，也不执行启动计划。

## 1. 三个独立维度

安装／登记清单表示有哪些程序。启动计划表示本次启动哪些程序；`after` 表示启动前置条件，`startupOrder` 表示操作者明确选择的执行顺序。能力绑定只选择通信契约提供者，不自动生成启动依赖。

例如安装 A、B、C、D、E，计划选择 A、C、D，并声明 C 在 A 后、D 在 C 后，就依次验证启动 A → C → D。B、E 保持停止，之后可各自审阅启动。未选择的前置不被暗中带起；若尚未就绪，相应计划成员显示阻塞。

顺序以实际的模块就绪报告、健康检查与全部声明桥连接为准，不使用固定等待秒数，也不承诺某项业务已完成。没有依赖的成员也可明确选择先后；声明与顺序不构成并发执行保证。

可选的 `startupOrder` 必须列出当前全部成员 ID 各一次，包括暂不加入计划的成员。不能包含重复或未知 ID，所有显式 `after` 前置必须排在该成员之前。冲突拒绝并说明原因，不偷偷改顺序或添加前置关系。实际执行按该顺序过滤未选成员；前置未选中仍不自动带起。未声明精确顺序时按声明生成稳定拓扑顺序。

例如安装顺序为 A、B、C，三个成员无前置时可明确保存 `startupOrder: ["C", "A", "B"]`，随后按 C → A → B 启动。若 A 声明 `after: ["B"]`，该顺序将被拒绝，需先把 B 排在 A 之前或由作者／操作者明确修改前置。

## 2. 整合包

两种预设均使用当前组件字段：`autostart` 缺省 true，false 表示不加入初始计划；`after` 是显式启动前置。切换 Atomic／Mesh 不重写这些声明。

- Atomic 的初始全成约束只针对本次选中的成员；选择的成员失败或受阻时清理本次所属进程，不要求启动安装清单中的其他模块。
- Mesh 缺省独立处理非关键失败，并继续无依赖成员；关键失败和显式 fail-fast 保持整包停止语义。
- 全部取消勾选时，两种预设都允许仅 Hub 运行，所有成员保持 stopped／neverStarted，入口 URL 为空。
- “仅启动 Hub”是本次执行选择 `startupMode: "hub-only"`，不修改保存的计划；正常启动使用 `"plan"`。执行模式必须进入本次启动审阅，不能在接受之后替换。
- 计划外成员以后通过既有精确运行／修订审阅独立启停。主动停止关键成员不是意外故障。

全部源码与锁定解释器仍在部署前预检；不承诺未启动 Python 模块缺少解释器时也能绕过环境核对。当前 Mesh、部分启动和仅 Hub 模式只在 trusted-local 支持；不支持的隔离组合在执行前拒绝。

## 3. 全局 Hub

Launcher 为当前全局 Hub 保存一份启动计划，包含明确登记的成员、是否启用、前置及失败处理。保存计划只改变下次执行的配置，不运行、不停止程序。未列入计划的登记程序仍可独立使用；外部自管会话不属于 Launcher 可启动的成员。

首次计划为空；新登记程序缺省不选中。当前格式为 `world-hub.launcher-startup-plan/v1`，成员为 `{programId,enabled,after:[]}`，可选 `startupOrder` 与整合包采用相同顺序规则，`onFailure` 为 `continue-independent` 或 `stop-plan`，`revision` 是规范化计划摘要。所有 ID 必须来自受管登记，前置不能自指、重复或成环。

| Launcher API | 行为 |
| --- | --- |
| `GET /api/programs/startup-plan` | 读取当前计划与受管程序 |
| `POST /api/programs/startup-plan/save` | `{plan,expectedRevision}`，只保存配置，变更修订不匹配则拒绝 |
| `POST /api/programs/startup-plan/review` | 空对象请求，生成当前代码与计划的有限期执行审阅 |
| `POST /api/programs/startup-plan/start` | `{reviewId,accepted:true}`，返回 202 操作编号 |
| `GET /api/operations/:id` | 观察逐成员进度与最终结果 |
| `POST /api/operations/:id/cancel` | 取消当前计划尚未完成的启动与排队 |

这些接口沿用 Launcher 的会话认证、CSRF、Host 与 Origin 检查。计划审阅不包含通信令牌，也不被持久草稿恢复为执行授权。

执行前展示具体程序、版本、源码、解释器、权限、公开配置、能力接线和计划顺序，用户明确接受后才执行。计划修订、源码、解释器或接线改变使旧审阅失效。逐项开始前重新核对，不以批量操作放宽原单项审阅。

已在当前 Launcher 真实拥有的运行成员，重新核对就绪和桥连接后跳过，不自动重启。未知进程归属、遗留 PID 或外部会话不能被接管。未选择的前置只有确实已运行且就绪才可满足依赖。

全局计划的失败处理不同于整合包整组生命周期：

| 选择 | 行为 |
| --- | --- |
| 继续无依赖成员 | 失败项记录错误，依赖项受阻，无依赖的选中项继续 |
| 停止后续计划 | 当前失败后不再启动后续项，已成功成员及原有成员保留 |

取消停止当前尚未完成的启动和后续排队，已完成成员保留并报告部分结果。停止全局 Hub 则取消相关启动任务，等待其实际清理，再停止属于该 Launcher 的程序和 Hub。清理未确认时保留归属及失败诊断，不能把它当作普通成员失败继续执行。

执行结果分别列出已启动、已运行跳过、受阻、失败、未执行或已取消；任务接受不等于启动成功。计划运行期间的修改与单项操作须通过同一管理队列和修订检查，不能更改正在执行的快照。

## 4. 装配与版本

全局 Hub 工作台快照保留计划成员的 `autostart`、`after` 和精确 `startupOrder`，可以导出 Atomic 或 Mesh 包。原组合更新在确认受管程序停止后，将公开参数、接线、执行顺序与计划失败处理一起审阅保存，组合版本必须提高；失败恢复原配置与计划。

全局 Hub 的组合版本采用与整合包一致的来源／改装标识：首次经审阅改装保留来源版本和来源摘要，后续提高组合版本并递增改装修订。Hub 内核发行版本另行显示，不把内核版本当作组合的来源版本。内容修订 SHA-256 不是界面上的改装次数。

`packType`、整包故障策略与 `critical` 仍不是全局独立程序的运行属性。若草稿试图将这些声明应用于全局 Hub，明确提示另存整合包，不能静默丢弃。全局计划自身使用“失败后继续无依赖项／停止后续”策略，不意味着关闭其他共享程序。

## 5. 工作台入口与恢复默认

全局 Hub 和整合包统一在工作台 `creator-tabs` 的“启动计划”页签编辑。详情入口直接载入相应真实源码或运行装配，再定位该页签；执行审阅与运行进度仍属于实际启动操作。

工作台共同提供成员选择、显式前置、编号顺序、上移／下移与指定位置。调整只保存草稿，不立即启停，不绕过组合新版本与停止审阅。全局计划的失败处理与整合包生命周期保持各自准确含义，不为外观一致而改变其他程序的进程归属。

“恢复默认”明确恢复**当前已保存版本的启动计划**，不是最初来源的计划，也不是清空计划。它只撤销本次计划编辑，不改源码、参数、能力接线或程序状态。草稿另行新增的模块保留，移出的模块不复活；恢复只应用当前仍在草稿中的成员并明确说明不能恢复的前置。用户仍可审阅保存为下一个组合版本。

## 6. 验收

验收须包含真实成员选择与顺序、未选择成员 PID 为空、未选前置不暗启、后续单独启动、全手动或仅 Hub、Atomic 选中集合失败清理、全局已有运行成员不重启、失败分支与取消、审阅漂移拒绝、计划持久化及工作台往返。浏览器核对中英文、窄屏、明确接受和任务结果；分发包核对新增文件及实际跨语言通信。

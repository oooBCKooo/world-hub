# 用途演示整合包

这三套演示把真实独立进程、双向 mod 桥、Hub 和浏览器探索界面组合到一起，帮助开发者试验接线、阅读通讯合同、替换业务模块。它们与默认 Hub 部署分开启动，各次运行使用自己的数据目录。

| 场景 ID | 用途 | 重点观察 |
| --- | --- | --- |
| `event-desk` | 多源事件台 | 两个来源独立发布，界面抽取信息，再经桥返回控制信息 |
| `modular-assistant` | 分布上下文助手 | 系统提示词、对话、材料来自独立程序，上下文组装与 harness 执行也在 Hub 外 |
| `digital-world` | 外部数字世界 | 世界状态、行动规则和 NPC 分别由外部程序负责，多轮通讯产生可观察的变化 |

Hub 负责接纳、寻址、留存和传递通讯。它不运行模型、决定上下文顺序、推进世界时钟、执行 NPC 或安排业务工作流。演示里的固定角色、主题、输入格式及规则属于这些外部程序，可以另行设计；无需把新的业务 `kind` 加进 Hub。

## 从源码探索

需要 Node.js 22.4+，无需安装 npm 运行依赖，也无需 DSH、模型账号、Python 或 PowerShell SDK 环境。在仓库根目录选择一个入口：

```powershell
npm run demo:events-explorer
npm run demo:assistant-explorer
npm run demo:world-explorer
```

也可以直接选择场景和是否打开浏览器：

```powershell
node examples/purpose-demos/run-demo.mjs --profile event-desk --check
node examples/purpose-demos/run-demo.mjs --profile event-desk --open
```

`--check` 只读检查环境与需要的文件，不启动进程、不创建数据目录。启动后保留终端，用浏览器打开启动输出给出的探索地址；若未指定 `--open`，手动打开该地址即可。需要停止时在所属终端按 Ctrl+C，等待启动器关闭自己创建的程序。

在“试一试”的“选择操作”中选一项，可编辑“发送的 JSON 信息”，再点击“通过 mod 发送”。右侧“程序返回的成果”展示目标程序响应，下方“信息流”可展开通讯信封。“程序与桥”展示实际连接；“枢纽管理”进入该独立 Hub 的管理页，“下载探索记录”导出探索界面记录。切换操作会重新载入该操作的默认 JSON。

默认运行数据写入 `data/purpose-demos/<场景>/<本次运行目录>`，每次运行相互隔离并保留记录。可用 `--state-dir '<自己尚不存在的新运行目录>'` 显式指定位置；已有目录会被拒绝，避免覆盖或共享会话数据。Hub 日志与外部程序状态分别保存，停止、读取和业务回应不等于提供者释放信息。记录只覆盖本次演示运行，不应把新的独立运行当成上一轮业务的自动续接。

## 三条探索路线

### 多源事件台

环境传感器、行情事件源、汇总程序和探索界面都是外部程序。传感器有采样输出与参数通讯两座 mod 桥；汇总程序订阅来源事件，界面通过自己的 mod 请求汇总和控制来源。

1. 先等“信息流”出现环境与行情的采样事件（来源默认约 1.4／1.8 秒采样一次），再选择“读取多源汇总”。刚启动时汇总可能尚为空。
2. 选择“调节采样参数”，使用预置的 `intervalMs: 900`、`offset: 3`，再执行“请求环境读数”，确认变化由来源程序返回。
3. 选择“注入环境偏移”，观察 Hub 接纳回执和来源随后发布的变更事件。回执只说明通讯接纳，不等于来源已完成业务。
4. 选择“调节行情参数”，再读汇总，观察另一个来源独立变化。

编辑 JSON 可以尝试其他数值。这个来源样例自行约定 `intervalMs` 为 250–10000 毫秒、`offset` 为 -20–20；这些是演示业务的校验范围，不是 Hub 对信息种类的规定。

汇总结果的 `latest` 保留来源数据 `value`、桥身份 `from` 与消息序号 `seq`；读数返回的 `bridgeMapping` 可对照同一传感器的两座桥。业务程序将采样参数保存在各自的 `source-state.json`，汇总保存在 `summary-state.json`。

可先把行情来源换成自己的采集程序，或将传感器的两座桥改成不同语言实现。采样周期、数值与偏移的意义由来源程序解释；Hub 不解释这些参数。此处行情数值属于演示数据，不是实时市场服务。

### 分布上下文助手

系统提示提供者、用户对话提供者、参考材料提供者、上下文组装程序、模板 harness 和探索界面分别通讯。组装程序请求三个来源，再把组装结果交给独立 harness；返回结果包含来源与完整上下文，便于检查“输入来自哪里”。

1. 选择“运行分布上下文”，观察多个来源的请求、组装与 harness 返回。
2. 依次尝试“修改系统提示”“增加用户对话”“修改参考材料”，再执行“运行分布上下文”，检查新的输入是否出现在上下文和结果中。
3. 阅读 harness 实现，区分确定性模板输出与真实模型推理；随后尝试以自己的程序替换一个提供者或 harness。

“运行分布上下文”的 JSON 里可修改 `prompt`。组装程序先将本轮问题交给对话提供者保存，取得系统词、对话与材料，再调用 harness；收到模板回答后，它再次请求对话提供者保存回答，形成多轮历史。

结果的 `context.systemPrompt`、`context.messages` 和 `context.material` 展示组装内容，`sources` 与 `harness` 记录实际响应主体、桥和消息序号。`modelInvoked: false` 和 `mode: "deterministic-template"` 表明这里没有模型调用。组装程序保存 `last-result.json`，对话提供者保存用户消息及模板回答。

可从文本文件、数据库、编辑器或其他已授权来源提供上下文。系统词与用户对话都属于上下文，但它们的角色、顺序、选取和转换由组装程序决定。给系统提示增加一个来源不需要 Hub 认识“系统提示词”这一业务种类。

### 外部数字世界

世界状态、行动规则、NPC 行为、多轮导演和探索界面分别是外部程序。导演每轮经 Hub 请求 NPC 决策、规则计算和状态提交，最后返回轮次记录。Hub 不持有业务世界，不主动推进这些轮次。

1. 先执行“读取世界状态”，再执行“推进 3 轮世界”，对照返回的每轮记录与状态变化。
2. 执行“注入 NPC 倾向”，观察 NPC 程序发布设置事件，再推进世界，检查外部行为实现的变化。
3. 执行“运行休整回合”，观察相同通讯组合如何承担另一种业务行动。
4. 执行“重置演示世界”，只重置状态程序的业务数据；已有 Hub 通讯记录继续保留。

“推进 3 轮世界”的 JSON 可修改 `rounds` 和 `action`。演示导演约定每次 1–12 轮，行动可选 `scout`、`rest`、`trade`；流程与限制由导演和规则程序解释。

结果的 `timeline` 展示每轮结果，`finalState` 是最终状态，`receipts` 给出状态／NPC／规则程序的响应身份与消息序号。状态程序保存 `world-state.json`，导演保存 `last-run.json`；这些业务文件位于各自程序目录中，不是 Hub 的世界模型。

可以独立替换状态存储、规则或 NPC 行为，也可以新增渲染程序订阅事件。让导演决定流程、让状态程序决定状态提交，避免把世界规则加入通讯核心。

## 构建可分享的演示包

源码包使用接收者本机的 Node。默认构建全部三个场景：

```powershell
npm run build:demos
```

也可以只构建一个场景，并把输出放到新的目录：

```powershell
npm run build:demos -- --profile event-desk --output-root dist/event-desk-source
```

Windows x64 便携包携带已校验的官方 Node 22.23.2、许可和来源记录。先准备一个新的运行时缓存目录，再构建：

```powershell
node scripts/release/prepare-runtime.mjs --download --output .artifacts/runtime/demo-node-win-x64
npm run build:demos -- --runtime .artifacts/runtime/demo-node-win-x64 --output-root dist/purpose-demos-portable
```

构建器也接受 `--profile modular-assistant`、`--profile digital-world` 或 `--profile all`。未指定输出根时使用 `dist/purpose-demos`。输出名称为 `world-hub-<版本>-<场景>-source` 或 `world-hub-<版本>-<场景>-win-x64`，同时生成邻接的 ZIP、`.zip.sha256` 与 `.build.json`；已有目标会失败，不覆盖旧包。生成物与运行数据不提交源码 Git。

完整解压某个 ZIP 到新目录后：

1. 运行 `verify.cmd`，检查包内文件与 manifest 的 SHA-256 是否一致。
2. 运行 `check.cmd`，检查环境与演示文件。
3. 运行 `start.cmd`，启动对应场景并打开浏览器。终端保持运行，Ctrl+C 停止。

便携包优先使用包内 Node；源码包使用 PATH 中的 Node。包中的 `demo-profile.json` 固定该包的场景，避免误启动另一个用途。全部演示模块源码仍随包提供，便于阅读和再构建。

`verify.cmd` 校验完整性，不启动通讯、不验证业务结果。仅 `data/**` 可变；编辑 UI、模块或其他原始文件会产生预期的完整性差异。正式分享修改后的演示应从源码重新构建。manifest 能发现文件变化，但不是发布者签名。

## 阅读与替换模块

从 [演示源码入口](../../examples/purpose-demos/README.md) 开始，先识别场景的程序、桥、主题与通讯合同，再替换一个业务模块。建议按下面的顺序探索：

这套演示启动器默认启动 Node 的 `peer.mjs`，`profiles.mjs` 是示例接线声明。只改 profile 不会自动加载任意外部可执行程序；替换为 Python、已有软件或其他运行时，须自行启动对应程序并调整演示启动器与接线。启动器在本次数据目录生成 `hub.json`；包内 `config/hub.json` 是正常部署的参考配置，编辑它不会改变演示会话的权限。

1. 启动原始场景，提交一次界面操作，记录请求、响应和程序身份。
2. 只改一个外部模块，例如换一个事件来源、上下文提供者、harness 或 NPC 行动实现，保留与相邻程序约定的通讯格式。
3. 新增主题或 `body.kind` 时，让对应 mod／程序声明并处理，同时在接线配置中授予必要权限；Hub 不枚举这些业务种类。
4. 为同一程序增加另一座桥时，分别管理连接、订阅和游标。桥共享 credential 是否共享稳定主体、配额和释放归属，须由程序按信任关系选择。
5. 再执行原始场景和自己的新增链路，分别记录通过范围。

换语言时可采用 [JavaScript／Python／PowerShell 接入材料](../onboarding.md)，也可直接实现 wire。通用 Hub 通讯合同与外部程序业务合同需要同时满足；“可以连接”不意味着双方自动理解上下文、事件或世界状态。

## 验证与边界

```powershell
npm run test:demos
```

演示测试应以真实独立程序经 Hub 的请求、注入、返回和业务结果为依据。浏览器操作、源码链路测试、实际 ZIP 解压后的包验收是不同证据，结果须分别记录。`--check`、manifest 通过或压缩成功都不能替代运行验收。

助手的 harness 是确定性本地演示实现，明确展示输入和输出，不调用在线模型、不启动 DSH。接入真实模型或 DSH 时，把它放进独立 harness 程序，保留对应通讯合同；凭据、工具权限和上下文处理由该程序负责。另有 [真实 DSH 的分布式上下文示例](distributed-context.md) 和 [DSH 验证说明](../verification.md)。

数字世界是有限的可观察业务样例，不代表完整世界引擎。三套演示均用于开发探索，不提供成品智能系统、生产业务资格、任意第三方桥、跨机器或无限容量的保证。容量、授权、释放策略与长期运行仍需按自己的部署验证，参见 [现行规格](../specs/index.md) 和 [验证范围](../verification.md)。

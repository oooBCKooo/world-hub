# 多来源上下文与外部 harness

这是外部程序验证方案，不是 Hub 业务规范。

## 1. 目标与参考方案

示例涉及普通外部程序：**多个上下文供给程序、界面程序、harness 程序**。上下文可以由分布的任意多个程序提供；本例把系统提示词、对话历史和资料分别交给三个独立来源，另通过配置加入第四个来源验证扩展。它们通过各自的 mod 桥与 Hub 通讯；Hub 对它们采用同一套身份、动态通道登记、发布、订阅、授权、游标和确认合同。

示例 harness 接入用户安装的 `@deepseek-ai/dsh`。安装位置通过 `PEROS_DSH_ROOT` 指定，不把个人机器路径写进源码。隔离测试可运行真正 DSH 和确定性本地模型；真实使用的 provider、model、home、工具许可和用户配置由外部程序选择，方法见[验证](../verification.md)。

源码 `examples/distributed-context/` 包含独立上下文、浏览器界面和 harness 程序。上下文包括系统提示词和用户对话，其内容、角色、顺序和接入 DSH 的方法由这些程序处理，Hub 只传递载荷。示例 Schema、流程和 DSH 适配接口不是 Hub 合同。

**Hub 只规范通讯形态，不能规定程序形态。** 这些名称表达用户希望参与测试的程序用途，不是 wire 协议角色，也不限定程序数量。它们可以是已有程序、插件、sidecar、独立进程或其他实现；可以共用宿主，也可以分别部署。桥如何和程序本地交互由适配方决定。上下文组合、来源选择与对话维护在程序侧实现。

本篇不定义上下文的内容／格式／生成策略、界面的布局／组件／GUI 或终端形态，也不定义 harness 的工具执行、审批、模型、资源管理或业务成功语义。任何此类合同由参与程序自行声明，不成为 Hub 的隐式 API。

## 2. 所有参与程序都是同类通讯对端

```text
上下文来源A    ⇄ mod 桥 ─┐
上下文来源B…  ⇄ mod 桥 ─┤
界面程序       ⇄ mod 桥 ─┼─⇄ Hub：接入、主题路由、通讯记录
harness / dsh  ⇄ mod 桥 ─┘
```

箭头表示信息可以双向流动，不要求一次实际业务会话使用全部路径。每个程序按自身约定决定何时发布、订阅什么、是否读取保存范围内的历史。测试流经 Hub；程序自己的本地接口和适配方式不由此图规定。

| 通讯能力 | 上下文供给程序 | 界面程序 | harness 程序 | Hub 责任 |
| --- | --- | --- | --- | --- |
| 发布信息 | 可以 | 可以 | 可以 | 按身份、主题和载体规则接纳并路由 |
| 订阅信息 | 可以 | 可以 | 可以 | 按主题过滤器和主题授权投递 |
| 按 cursor 获取历史 | 可以 | 可以 | 可以 | 在保留范围内补课并报告缺口 |
| 提交消费确认 | 可以 | 可以 | 可以 | 验证 ACK、释放窗口、推进连续确认水位 |
| 回传结果／反馈 | 可以 | 可以 | 可以 | 传递关联信息，不解释业务结果 |
| 自行登记通道和发收方向 | 可以 | 可以 | 可以 | 接受合法声明，不建立内置业务通道目录 |
| 决定自己发布记录的留存 | 程序自行决定 | 程序自行决定 | 程序自行决定 | 默认保护，仅提供者明确release允许清理 |
| 定义内容、表现或执行 | 程序自行决定 | 程序自行决定 | 程序自行决定 | 不参与 |

这些都是普通通讯能力，不存在界面专用的 Hub 世界状态或 harness 专用的 Hub 工具执行入口。

## 3. 接入与双向收发

各桥实现当前 [通讯契约](../specs/protocol.md)，使用配置允许的通讯身份和主题规则。`hello` 中如有 `role` 或 `displayName`，仅为诊断注解；不得由 `context`、`ui`、`harness` 等文字获得路由、权限或执行资格。Hub 不识别这三个业务用途。

通道由 mod 动态登记。显式登记使用 `register` 帧，字段为 `requestToken` 和 `channels: [{ name, publish, subscribe }]`；Hub 回 `registered` 并回带 `requestToken`。发布方向的 `name` 是具体合法主题，订阅方向可为合法过滤器；声明两方向时分别校验。登记受当前主题 ACL 限制，不产生新授权。

发布和订阅也构成 mod 的隐式登记，保留既有桥的接入路径；不要求运维或 Hub 源码先列出每一种业务通道。允许订阅未来或尚无生产者的主题。通道声明是随连接清理的通讯信息，不携载荷 Schema 或业务 handler，也不决定程序形态。

通用收发路径为：

```text
程序 A → 本地桥 → publish(topic, body) → Hub
Hub → delivery → 程序 B 的桥 → 程序 B
程序 B → 本地桥 → publish(约定主题, 约定内容) → Hub → 程序 A
```

参与程序可以任选其他接收者、主题与约定，Hub 按同一规则处理。`published` 只表示 Hub 接纳该次通讯，不表示接收程序已消费，更不表示上下文生成、渲染或工具执行成功。程序需要反馈时，另以自己的应用约定发布反馈消息。

发布时可以没有接收者。后来接入的程序通过同一按游标抽取接口读取；读取、ACK和caught_up都不清理信息。提供者按自己的策略经mod的release许可回收自己的记录，枢纽只检查通讯归属和容量，不根据程序用途决定保留或删除。释放后仅允许后续历史段轮转，容量满且无法清理时明确拒新，不能覆盖未释放记录。

当前代码对应是 [Hub 的帧处理和动态登记](../../src/hub/lib/hub.mjs)、[主题路由](../../src/hub/lib/router.mjs) 和 [Bridge 的收发接口](../../sdk/javascript/bridge-kit.mjs)。它们是通用通讯入口，不构成上下文业务实现。

## 4. 按 cursor 抽取保存范围内的历史

三者使用同一种历史路径，不新增 `get_context`、`get_ui_state` 或 `run_harness` 等 Hub 业务接口：

```text
subscribe(filters, from: N)
    → subscribed（订阅建立与补课目标水位）
    → delivery（匹配的历史消息）
    → 桥或程序提交消费确认 ack
    → caught_up（补课扫描／发送进度）
    → 继续接收实时消息，或由程序解除订阅 unsubscribe
```

- `N` 是 Hub 日志序号，抽取的是 `N` 之后、符合主题过滤器且仍在保留范围内的消息。省略 `from`、手工数字与桥侧续订游标的语义采用 [可靠性与访问边界](../specs/reliability-access.md)。
- `caught_up` 是通讯补课的扫描／发送水位；它不等于收到的内容全部消费完成，不等于上下文完整，也不等于程序业务任务完成。消费确认水位与扫描／发送水位应分别解释。
- 每座桥／每项订阅的消费进度独立。程序按其消费边界确定何时提交确认；Hub 只校验该订阅 ACK 的通讯有效性，不能读取“工具是否成功”作为确认前提。
- 需要一次历史抽取时，程序可记录 `subscribed` 的补课目标水位，将目标区间与后续实时流在本地分别处理，并在完成自身所需的消费后解除订阅。当前接口不是独立的分页历史查询或世界快照 API。
- 收到 `catchup_truncated`、`overflow` 或连接失败时，明确记录范围、原因与已取得的水位；不能把缺失消息补造为事实，也不能把“拿到了当前保留区间”说成“完整历史已恢复”。

上下文供给程序可以使用历史，也可以使用实时流、自己的存储或其他输入；这属于其程序选择。界面和 harness 也可使用历史，Hub 不将历史能力专属化。

## 5. 程序自行约定的信息关系

程序可以通过自己的配置、公开说明或消息约定确定输入输出 Schema、用途、版本、主题和反馈含义。程序自协商本身也可使用普通消息，Hub 只转交，不解析协商内容、选择能力提供者或授予应用权限。

以下只是参与程序可选择的应用约定示例，**不是 Hub 保留命名空间、规定角色或默认接线配置**：

| 可选约定 | 用途 | Hub 看到的事实 |
| --- | --- | --- |
| `demo/request` | 某参与程序发布一份请求 | 一个合法主题与对象载荷 |
| `demo/result` | 其他程序发布其自行定义的结果 | 同样的一条消息 |
| `demo/feedback` | 消费者反馈它自行判断的情况 | 同样的一条消息 |
| `id` | 程序赋予消息的标识 | 按当前 wire 合同传递的元数据 |
| `correlation` | 程序关联同一应用会话或工作链 | 元数据，不是 Hub 业务会话／授权 |
| `replyTo` | 程序声明回应某消息 | 元数据，不是 Hub 对业务成功的认证 |

约定中可以包含应用用途和任何合法数据结构，校验、适配、解释和是否接受它们由参与程序决定。桥包 manifest、应用 Schema、能力发现、UI 模型和 harness 工具清单可以在适配方发展；本篇不要求把它们注册为 Hub 内部对象。

应用的信息种类可放在 `body.kind` 或双方约定的其他载荷位置；它与 wire 的 `type: "publish"` 等通讯操作不同。Hub 不穷举 kind 值、不要求选择内置信息类、不以其调用 handler。mod 新增合法通道或传递新种类的信息无需修改 Hub 源码，仍须符合通讯帧语法、上限和通用主题 ACL。

## 6. 消费确认、业务结果与恢复

程序或桥提交 ACK 表示它按照自己的消费边界确认了某条投递。Hub 根据订阅、有效投递序号和连续确认水位维护通讯进度；Hub 不据此判断程序完成了哪些业务操作。消费失败时，程序决定不确认、记录失败、重新消费或采取自己的恢复策略，遵守当前通讯窗口和缺口合同。

业务结果可以是成功、失败、待处理、未知或其他应用声明；Hub 原样传递其合法载荷，不将 `published`、`ack` 或 `caught_up` 改写成业务成功。UI 如何展示、上下文是否可用、harness 的工具是否真的执行，分别由拥有该事实的程序判断。

历史消息和重连投递可能再次到达。Hub 不判定载荷是命令还是观测；对会产生外部效果的信息，消费程序自行决定期限、意图标识、去重、结果核查和历史消费策略。未确认真实效果时不得因通讯重连自动把应用结果改成成功；需要模拟或只读重放时由程序采用相应执行通道。

Hub 的主题权限仅控制通讯。dsh 的系统权限、工具准入、用户身份、审批和本地执行由 dsh／harness 或其实际宿主管理，本篇不默认授予任何权限。

## 7. 验证和替换边界

默认 Node 测试覆盖上下文程序、界面上下文处理与 JSON-RPC 传输；真实 DSH 的最小链路、重启和进程关闭是显式 `npm run test:dsh` 集合，要求自己的实际安装，不会静默以 mock 替代。入口 `npm run demo:context` 使用真正 DSH 加隔离本地测试模型。完整方法见[验证](../verification.md)。

源码通过配置更换全部主题、增加第四个独立来源以检查任意 mod 接入，不将固定系统提示词／对话／资料三类变成穷举。上下文完整性、模型质量、工具效果、真实 API 和 ACP 仍需程序自身验收；本机通讯测试不能冒充跨机器部署。

参与者可替换任一程序、增加来源或改变其本地接口，不需 Hub 增加专用业务角色、内容结构或工具执行器。若确实需要新的通用通讯能力，按通讯合同和实际验证单独推进，不能由一个应用草案推断已经支持。

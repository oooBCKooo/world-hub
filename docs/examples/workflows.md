# 多轮信息流与外部工作流程序

示例验证外部程序逐跳通讯：`A → 枢纽 → B → 枢纽 → C → 枢纽 → D → …`。接收者也可以成为下一条信息的提供者，调用别的程序、返回上游、再次访问之前的程序，或由程序分支、汇合。程序数量、轮数、路径和信息种类不在枢纽中枚举。

工作流示例目标包括独立工作流程序的可行性：该程序通过 mod 接收工作请求，自行执行多轮工作，每轮联系多个程序并收集结果，将前轮输出交给下一轮，最后经 mod 返回成果。计划和轮间屏障属于工作流程序，枢纽不代其执行计划，也不判断成果是否满足业务目标。

## 职责与通讯

每一跳使用现有 mod 动态通道、发布／订阅、定向注入或请求／回应。wire 0.1、`directed-v1`、`blob-v1` 支撑这些通讯；没有 Hub 流程执行器或内置业务协议。

程序收到信息后，自行处理并经自己的 mod 发出下一条消息。每跳生成自己的 seq，发送者、提供者与 session 由认证连接确定。后一跳不是原消息自动改地址，也不会继承前一提供者的通讯权限。

| 事项 | 负责方 |
| --- | --- |
| 下一程序、继续／结束、分支、汇合、拒绝、重试、调用等待、业务去重 | 外部程序与 mod |
| 通道声明、按原合同发送和抽取 | mod |
| 每跳接纳、认证身份、主题权限、目标过滤、留存及附件字节传输 | 枢纽 |

`flowId`、`route`、`trace`、轮次、分支名等可以是程序自定义正文。枢纽原文传递，不解释这些字段，不借此推导下一跳、保证顺序或决定业务完成。验证程序中的这些字段只是该夹具的约定，不是通用程序必须遵循的形态。

## 调用、循环与恢复

多层调用仍逐层建立独立请求。例如 A 调用 B，B 调用 C，C 调用 D；D 回应 C，C 以自身身份回应 B，B 再回应 A。每个可信回应分别绑定对应的原 requestSeq，返回地址按原请求推导。不能用正文中的关联字段代替这条绑定。

程序可以回访同一程序。是否终止循环及等待哪些分支由程序决定。单个订阅处理器按桥的交付顺序等待处理；互相等待的循环调用可能形成应用死锁，程序需自行安排异步注入、不同订阅／桥或等待策略。

离线的稳定身份可后来抽取保留的信息；精确 session 仍只属于原连接。调用 Promise 的本地超时／断线不取消消息，也不自动恢复原等待。程序可以用自身 journal 记录已处理输入，在重启后识别历史重放。Hub 不去重业务，也不保证业务恰好执行一次。

示例 journal 场景只验证程序完成转交并记录 journal 后的受控重启。发送接纳与程序自身 checkpoint 之间仍存在崩溃窗口，不能将此场景写成断电或任意崩溃下的 exactly-once。

## 留存与大附件

到达终点、下一跳接纳、回应、读取和 ACK 都不释放前面的信息。每跳新消息属于该跳提供者，由其自行决定 release；新提供者不能代替上游释放。

附件所有权保持附件合同：中间程序可以读取获准消息的附件，但不能直接把他人对象 ID 附加到新消息扩大授权。需要再次提供字节时，中间程序自行下载并校验，再上传自身拥有的新对象。新副本、原对象及各条消息分别由其提供者决定保留策略。工作流夹具验证这种中转方法，不限定所有外部程序必须复制文件或采用这份夹具。

## 实际验收入口

```powershell
npm run demo:workflow
node examples/workflows/run-flows.mjs
```

演示执行独立工作流程序的多轮多程序工作，并返回最终成果。完整集合包含 10 个独立进程场景，纳入默认 Node 验证；源码见 `examples/workflows/` 与 `tests/integration/workflows/`。报告包含 PID、各跳 seq、认证地址、处理结果、退出、文件校验和源码 SHA-256，只有实际报告才能说明通过范围。方法见[验证](../verification.md)。
